# Council: socaity-ipg — Define the M0 first-contribution path end-to-end

Participants: community-builder, mechanism-designer, product-designer
Type: research · Priority: P0 · Was blocked by socaity-z61 (now adopted)

Issue:
- Context: M0's done-condition is "the ledger has recorded its first external contribution" — but what counts, how a stranger claims it, and what the ledger entry records were undefined at filing time.
- Question: Specify the path end-to-end: a stranger arrives at the manifesto → does something → an external ledger entry exists. Every step, every artifact, every actor.
- Why it matters: M0's done-condition; the launch cannot press "post" before this path is live (launch-strategist comment on file).

Adopted context binding this council (most of the path now exists — do not relitigate):
- socaity-z61: static site, contest workflow (issue templates → PRs), signed-patch courier path, tickets-as-files, CONTRIBUTING.md, SLO, seeded good-first-disputes, weekly digest.
- socaity-19p: 0.5 vu minimum-entry floor, ticket-free for trivial accepted contributions (contribution.trivial_accepted); artifact work via pre-opened tickets; founder gates inclusion never value.
- socaity-zyt: genesis prologue must complete (through epoch.opened(1)) before the first external entry; event types work.logged / ticket.accepted / contribution.trivial_accepted; mandatory fields incl. mode election, category, evidence hash.
- socaity-7mk: contributor = self-held Ed25519 keypair; in-browser keygen is M1+; at M0, keygen instructions + signed-patch or GitHub-attested linkage; entries signed.
- Remaining scope for THIS council: the exact end-to-end walkthrough (incl. WHO signs the ledger entry when the contributor came via GitHub PR and has no keypair yet — does the first-contribution flow require keygen, and how is that made non-fatal friction); what the ceremonial first entry records; how the moment is celebrated/communicated; failure modes (contributor bounces at keygen; contribution rejected; two contributors race for "first").

## Round 1

### [community-builder]
PROPOSAL (owner). **Walkthrough:** (1) Arrival — manifesto carries ONE call to action: "Claim the first external entry on the ledger" → /roadmap strip + CONTRIBUTING.md. (2) Orientation — worked example + the 5–10 seeded good-first-disputes; stranger picks typo fix / dispute / pre-opened T1 ticket. (3) Contribution, GitHub path — issue-template dispute or web-editor PR; no keypair, no ledger specs; <24h SLO. (4) **Acceptance — the merge is the moment of belonging; it must not wait on anything ledger-side.** Warm merge comment names what changed and carries the claim invitation. (5) **The claim — keygen HERE, after merge, never before:** at maximum motivation (sunk effort, warm response, being OFFERED something) a 2-minute CLI step converts; pre-contribution keygen converts like a cookie wall. One-page claim doc: keygen, bidirectional GitHub attestation (7mk), submit key + entry ref. Courier-path contributors skip (key preceded contribution by construction). (6) Recording — genesis prologue complete first (site must not invite claims before epoch.opened(1)); founder signs the acceptance event (actor=founder, payload.contributor = new key, mode, category, evidence = merge SHA); accrual per 19p. Done-condition met. (7) Celebration.
**Key question answered from recruitment reality:** GitHub-only contribution recordable with key added later? **No — and it doesn't need to be.** 7mk bans retrofitting keys under recorded entries. Decouple the two acceptances: **merge instant and unconditional; ledger entry written only once the key exists.** The key precedes *its entry*, not *the contribution*; the merged PR waits in git as imperishable evidence. Bouncing at keygen costs the contributor their accrual, never their contribution, digest credit, or welcome.
**The first entry records nothing ceremonial — that is the point:** schema-v1 event indistinguishable from entry #10,000; firstness = chain position; ceremony lives entirely off-ledger.
**Communication:** personally first (founder thanks in-thread BEFORE public amplification; **asks consent before naming them anywhere** beyond the ledger's own record); permanent first-entry note on the ledger page; special-edition digest telling the path ("here's how to be entry two") — the first entry is a recruitment artifact; the telling makes the PATH look walkable, not the person exceptional; **honesty rail: if the first contributor is warm-circle, the digest says so.**
**Failure modes:** bounce at keygen — contribution stands and is celebrated regardless; one nudge after ~a week; claim open indefinitely (flag for MD: confirm the zyt staleness predicate doesn't time-box artifact claims; if it does, the window must be generous and stated). Rejected — z61 decision record, kind, pointer to seeded disputes; a rejected first-ever contributor who returns is the strongest culture signal. Race — chain position only; first completed claim wins; celebrate both stories ("first merged" and "first entry"); abundance framing, no founder discretion.
**PARAMOUNT:** no keygen as pre-contribution gate; no staged/solicited first entry (warm-circle fine DISCLOSED; manufactured never); no publicizing the first contributor's identity beyond the ledger record without explicit consent.

### [mechanism-designer]
**1. Deferred signing: an acceptable pattern exists — escrow-then-claim, forward-only.** zyt already has acceptance events maintainer-signed with contributor key in payload. Escrow variant: maintainer appends the acceptance with **payload.contributor = null plus mandatory claim_binding** = hash of the evidence-side identity the work proves (github:<account> — hash only, no plaintext handle on-ledger). Contributor later appends **attribution.claimed {escrow_ref, actor_key, attestation}** (the 7mk bidirectional linkage). Replay resolves attribution deterministically. **Not retroactive attribution:** 7mk bans mutating/re-attributing past entries; the escrowed entry never named anyone; the claim is a forward append, same family as key.rebound. **Anti-squat:** claim predicate fixed at escrow time by claim_binding — squatting requires compromising the cited GitHub account, the same trust boundary the evidence rests on; claimant races settled by chain order of first valid attestation. **Anti-honeypot: after N epochs (propose N=2) unclaimed escrows are claimable only via the zjr adjudication path** — escrowed value never expires; the prize gets a human gate once worth attacking. Keygen thus never fatal: the entry exists at acceptance; the key is needed only to OWN it — the correct incentive gradient (a reason to keygen, not a wall).
**2. Mode default: E, as a published protocol constant, never maintainer discretion** — a first-timer has no basis to elect a fixed price; for escrowed entries there is no contributor to elect at all, so a protocol constant or mode becomes a discretionary lever. Claim UI displays the recorded mode before signing.
**3. "First external contributor" gaming: assume unfalsifiable, remove the payoff.** Ledger claims only the mechanical fact (first entry with actor lineage ≠ founder keys); **founder pre-commits (hash on-ledger, before the launch post) the criteria for "external" and a disclosure pledge** covering prior relationships — converts undetectable puppetry into discoverable fraud against a public commitment (reputation-fatal, the only currency at M0). **No economic premium for firstness** beyond ordinary epoch-share earliness; celebrate the first cohort, not a podium. Credibility from third-party timestamps (public issue → PR → GitHub history), not platform say-so.
**PARAMOUNT:** no escrow without a mechanically evaluable claim_binding fixed at append time (else an attribution slush fund); no mutation at claim; no maintainer-chosen mode defaults; no first-contributor bonus/badge-with-value/multiplier; no indefinitely auto-claimable escrow (epoch-bounded, then adjudication — else honeypots priced in someone else's GitHub security).

### [product-designer]
**Friction profile — progressive commitment, four plateaus:** P0 (zero friction): manifesto → roadmap → dispute/PR; no key concepts anywhere on this stretch. P1 (pivot, peak motivation): the merge comment is the commitment-escalation surface: "Merged — thank you. A ledger entry is ready to be claimed: 0.5 vu against a key only you hold, permanently and publicly. ~2 minutes. It waits for you — there is no deadline." Framed as collecting something owned, not registering. P2 (the one real cost): /claim — three copy-paste blocks, <2 minutes. P3 (payoff): entry appended; reply with permalink to the ledger row.
**/claim page:** **primary tool ssh-keygen** (already installed everywhere; one toolchain serves claim + courier paths; no comparison table — choice paralysis is the failure mode this page prevents). Three numbered steps with one-sentence plain-language explanations: generate (the platform never sees the private half); sign the link string (proves account and key are the same person); **publish as a comment on your merged PR** (same attestation property as the gist, one fewer surface; gist stays the documented alternative + revocation home). Below the fold: passphrase guidance, "your key is permanent, your display name is not", collapsed alternates, pseudonymous/courier path link.
**Legibility contract:** merge comment → claim comment → founder reply "Recorded: [permalink]". The ledger row answers in one glance: name/truncated key, plain-words event type, 0.5 vu, evidence SHA → merge commit, chain position, "verify this yourself" link. **The permalink is the product**; build-time OG cards per entry are the entire shareability layer.
**Celebration:** ceremony is presentation-layer only; /ledger renders the genesis prologue as a readable timeline ending at epoch.opened(1); the first external entry is visually distinct **because that property derives from chain position**; first-N founding-contributors strip derived mechanically — defuses the race (publish the tie-break rule in CONTRIBUTING.md before it's needed; frame the cohort, not a winner). Aesthetic: quiet, archival, typographic — the celebration IS the auditability; "public record," never "airdrop."
**PARAMOUNT:** no keygen before acceptance; **no expiring or deadline-pressured claims** — urgency mechanics on an append-only ledger are a trust leak; no GitHub-handle-as-identity fallback on-ledger; no multi-tool chooser as primary; no hand-maintained firstness; no crypto-flavored celebration surfaces.
**Pre-launch tests:** (a) 5 devs complete /claim <3 min from the merge comment alone; (b) they can state unprompted what the private key is for and what loss means; (c) a stranger reads a ledger permalink in 30 seconds.

### Facilitator
Standing proposal: CB's walkthrough + PD's friction/claim/celebration design + MD's integrity rails (mode-E protocol constant, founder pre-commitment + disclosure pledge, no firstness premium, cohort framing).
ONE structural fork to settle in Round 2: **entry-at-claim (CB step 6, PD plateau 3: no ledger entry until the key exists) vs escrow-at-acceptance (MD: acceptance event appended immediately with contributor=null + claim_binding; attribution.claimed appends later).** Material consequences: (a) the zyt epoch clamp means entry-at-claim assigns a late-claiming contributor's observation to a LATER epoch (different D_e — the contribution is valued in the wrong epoch); escrow records it in the epoch the work was accepted. (b) M0's done-condition under entry-at-claim waits on the first contributor's keygen; under escrow it is met at acceptance — but note CB's done-condition reading requires an entry with "actor lineage ≠ founder keys": an escrowed entry is founder-signed with null contributor — does an unclaimed escrow count as "first external entry"? (c) Schema: escrow needs contributor-nullable acceptance + attribution.claimed + claim_binding in v1 (additive, decidable now). (d) PD's no-deadline paramount vs MD's N=2-epoch adjudication gate on auto-claims — PD to rule whether a security escalation (not expiry, not advertised as urgency) violates it.
Open objections: none standing; the fork is genuine — argue it.

## Round 2

### [community-builder]
**I move to escrow-at-acceptance — consent, not compromise; MD's design is better at the thing I own.** Bouncing at keygen now costs the contributor nothing at all; the epoch argument is decisive ("your work was valued in the wrong epoch because you took three weeks to run ssh-keygen" is a hospitality failure); "it waits for you" becomes literally true on-chain. **Condition of consent: M0's done-condition = first CLAIMED external entry** — an unclaimed escrow is founder-signed with contributor=null; every signature on the chain is still the founder's; by MD's own rail it mechanically fails "actor lineage ≠ founder keys", and "the founder wrote an entry about a person who has not appeared" is the *shape* of a staged first entry even when genuine. The claim is also the better launch beat: the moment the network gains its second sovereign key — what M0 was always secretly about. Riders: two celebrations honestly labeled (merge celebrated immediately and personally — belonging never waits on cryptography; the milestone announcement waits for the claim; the digest may narrate the gap); race framing cleaner under escrow (first-escrowed and first-claimed are two true stories; publish both rules); the N=2 gate is compatible with "no deadline" provided invitation copy never mentions it as time pressure; genesis prologue precedes the first escrow. **PARAMOUNT (sharpened): M0 is not announced as done, and no "first contribution recorded" story posts, while the first entry's contributor field is null. No exceptions for schedule pressure.**

### [mechanism-designer]
**Concede (b): an unclaimed escrow does NOT satisfy the done-condition — escrow for epoch correctness, claim for the milestone. Both.** Declaring at escrow is platform say-so about an unverified counterparty and is founder-self-dealable (escrow against a puppet account = M0 "done" with zero non-founder signatures) — it would convert my own pre-commitment rail into a fig leaf. **Done-condition = first attribution.claimed with actor lineage ≠ founder keys, valid against its escrow's claim_binding** — the first thing on the chain a non-founder key ever signs, which is what "external" honestly means. A milestone named "first external contribution" SHOULD be uncheatable by anyone holding only founder keys. **The staleness predicate settles the fork decisively:** under entry-at-claim, a three-week-late acceptance event carries week_ref > S stale and the validator REJECTS it — entry-at-claim forces either a hard ~2-week claim deadline (violating PD's paramount) or a validator exemption that reopens the backdating hole for everyone forever. Both worse than escrow. **Answer to CB: under escrow the claim is never time-boxed** — the accrual-bearing observation is appended at merge (always fresh, correct epoch, correct D_e); attribution.claimed is an attribution event: no week_ref, no quantity, no staleness, no epoch sensitivity; timing affects only when ownership resolves (and the post-N path hardening). The /claim page can say, truthfully and schema-backed: "your entry is already recorded in the right week; the claim only attaches your name, and it waits." **PARAMOUNT (revised): no milestone declaration on a chain bearing zero non-founder signatures; no staleness exemptions to rescue entry-at-claim.** CONSENT as amended.

### [product-designer]
**Ruling 1: I move to escrow-at-acceptance — it makes my P1 framing literally true instead of rhetorically true.** The permalink (the product) now exists at the moment of maximum motivation; the claim becomes exactly "collecting, not registering." It also fixes a fairness-legibility bug I missed: entry-at-claim would show identical contributions valued differently, explained only by keygen latency — illegible to any auditor. Conditions (presentation-layer): (1) **the unclaimed state is designed, not defaulted** — "attribution reserved — provably bound to the author of this merged PR; awaiting their signature"; never "anonymous"; first-class OG card; claim_binding hash below the fold as a verify-yourself detail. (2) "Yours" is honest copy (claim_binding mechanically reserves it) but comment and row must not contradict — row says "reserved for you, unclaimed". (3) Celebrate at claim, record at acceptance. **Ruling 2: the N=2 gate does not violate the no-deadline paramount** (value never expires; path hardening ≠ countdown; an indefinitely auto-claimable escrow is a honeypot and I will not defend a trust leak to avoid one) — **but the current copy does**: revise to "It waits for you — your entry never expires. After about [N in human time], claiming takes one extra verification step." Flat fact, no urgency styling; "epochs" never in contributor-facing copy; the current path always self-describing on the row and /claim page. Added pre-launch test: (d) a stranger reads an UNCLAIMED escrow permalink and states who it belongs to and why, in 30 seconds. CONSENT as amended.

## Resolution

ADOPTED by consent, Round 2 (all participants converged on the same amended package within the round; no objections standing).

**The M0 first-contribution path:**
1. **Zero-key contribution stretch:** manifesto (one CTA) → /roadmap strip → seeded good-first-dispute / T1 ticket → issue or web-editor PR. No key concepts before acceptance. <24h SLO; structural merge criteria; rejection = kind written decision record + redirect.
2. **Escrow-at-acceptance:** at merge, the founder appends the acceptance observation with payload.contributor = null + mandatory claim_binding (hash of github:<account> — no plaintext handle), mode = E (published protocol constant, never discretion), evidence = merge SHA, accrual per 19p (0.5 floor / ticket tier). Correct epoch, always staleness-fresh by construction. Genesis prologue through epoch.opened(1) strictly precedes the first escrow.
3. **The claim:** merge comment (warm, names the change) links /claim: ssh-keygen primary (three copy-paste blocks, <2 min target), attestation published as a PR comment (gist = alternative + revocation home), courier path for pseudonymous contributors (whose key precedes contribution). attribution.claimed appends forward — no mutation; anti-squat via claim_binding; races settled by chain order of first valid attestation; after N=2 epochs auto-claim hardens to zjr adjudication (value never expires). Copy: "your entry never expires; after about [human time], claiming takes one extra verification step" — no urgency mechanics, state always self-describing.
4. **Done-condition: M0 is done at the first attribution.claimed with actor lineage ≠ founder keys** — the first non-founder signature on the chain. No milestone announcement while the first entry's contributor is null; no schedule-pressure exceptions.
5. **Ceremony:** on-ledger, nothing — the first entry is schema-identical to entry #10,000; firstness derives from chain position. Off-ledger: merge celebrated immediately and personally (consent before naming, always); milestone celebration at claim; permanent first-entry note on /ledger; special-edition digest narrating the path (and the escrow gap as proof of how the ledger works); founding-cohort framing (first-escrowed and first-claimed both true stories; tie-break rules pre-published in CONTRIBUTING.md); warm-circle disclosed if applicable; founder pre-commits (hash on-ledger before launch) the "external" criteria + disclosure pledge; no economic premium for firstness, ever.
6. **Unclaimed state designed:** "attribution reserved — awaiting their signature"; first-class OG card; quiet archival aesthetic ("public record", never "airdrop").
7. **Pre-launch tests:** /claim <3 min from merge comment alone; contributors can state what the key is for and what loss means; stranger reads a claimed row in 30s; stranger reads an UNCLAIMED row in 30s.

Schema delta (additive, v1): contributor-nullable acceptance + claim_binding + attribution.claimed event — flows to socaity-mxu/zyt implementation.
