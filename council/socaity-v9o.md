# Council: socaity-v9o — Whose tokens run M1 decomposition: BYO agent vs hosted inference vs BYO-key

Participants: agent-engineer, platform-engineer
Type: decision · Priority: P1 · Determines socaity-xt4's remainder (agent-run observation payload + BYO attestation)

Issue:
- Question: Is M1 (a) a skill/CLI running inside the user's own Claude Code (BYO tokens, zero inference cost, limits UX and non-Claude users), (b) hosted with platform-paid inference (real per-repo cost during the grant bridge), or (c) BYO API key in a hosted UI? Decides M1 architecture, the cost floor on grant funding, and whether the first metered agent runs land on the ledger from day one.

Adopted context:
- sbb schema: agent writes carry provenance (on_behalf_of, model, prompt_hash, run_id); graph is repo files at M0, DB+event log at M1.
- zyt: agent-run observations enter as additive types when needed; metering must be auditable (x8o: compute credit backed by metered capacity).
- z61: static site M0; M1 = boring web app.
- 19p: timed/artifact work observation types exist; agent capacity converts via tokens-per-vu (rate delegated).
- M1 done-condition: "a stranger uses it on their own repo because it is the best triage tool available" (milestones.md).
- Grant reality: NLnet-scale budgets (€5–50k) — platform-paid inference at scale is not in the bridge budget.

## Round 1

### [agent-engineer]
PROPOSAL (owner): **staged hybrid — (a) as the M1.0 spine, (c) as the M1.1 metered on-ramp, (b) refused as default (permitted only as a hard-capped demo quota).**
1. **The stranger's first-run decides the shape:** under (a), a Claude Code user installs the skill, points at a repo, gets an AND/OR graph in their own terminal with their own tokens — zero signup, zero cost to us; the strongest first-run for that population, and it is doctrine (platform provides targets, context packs, verification — not a captive runtime). Under (b), the better the first-run works the faster it kills us on an NLnet budget. Under (c) alone, an API key is demanded before any value is shown — but it is the only first-run for non-Claude users. So (a) first, (c) close behind in the z61 web app.
2. **Quality control: separate evaluating-the-decomposer from validating-a-decomposition.** q8b runs where we control everything and gates the prompt/skill releases WE ship (applies identically under a/b/c since we author the prompts). BYO output crosses into the platform through a **submission gate**: schema/structural validation (granularity bounds, competing OR branches present, no orphan edges) + a platform-side LLM-judge rubric at ingestion — a garbage decomposition from a weird local config never lands unflagged. Refusing (a) because "we can't eval it" would be evaluation theater in reverse.
3. **Provenance: report honestly, don't fake attestation.** A skill can populate all sbb fields; prompt_hash is trustworthy-ish (we ship the prompt); model and token counts are self-reported. Add an explicit **provenance grade**: attested: self for (a)-path runs; attested: platform for runs transiting our proxy.
4. **Metering — PARAMOUNT: I refuse any design in which self-reported BYO token counts accrue vu.** x8o backs compute credit with metered auditable capacity; self-reported counts are Sybil-trivial inflation. Accepted consequence: M1.0 runs produce ledger observations (self-attested, calibration-useful) at **zero vu**. The (c) path makes metering ledger-grade: BYO key transiting a platform proxy that observes actual token usage — auditable without us paying for inference; the on-ramp for the first tokens-per-vu accruals. That is why (c) must ship in M1, not later.
5. **Budget:** (a) ≈ €0/run; (c) proxy hosting only; (b) unbounded. Exception: hard-capped platform-paid demo budget for decomposing M2-spotlighted repos — marketing spend with a ceiling, not architecture.
Second PARAMOUNT: no M1 release without the q8b golden-repo eval gating the shipped skill — the done-condition is a quality judgment; whose tokens ran it is irrelevant if the decomposition is confidently wrong.

### [platform-engineer]
**(a), with the platform shipping schema + validator + CI; (b) and (c) refused for M1** — (b) on cost, (c) on custody.
**(a) ships four dead-boring artifacts, none running inference:** the skill/CLI (intelligence lives in the user's agent; our value-add is prompt engineering, schema, local validator); the graph schema + `socaity validate` offline command (**we own the format, not the compute**); a CI conformance GitHub Action (zero secrets, contributor's Actions minutes); the M1 web app doing exactly three things — render, validate, ingest. Cost floor: tens of euros/month.
**(b) enumerated then refused (PARAMOUNT):** key custody + rotation; per-user auth/quotas before identity infra exists; abuse control (a free decomposition endpoint is a free LLM proxy, farmed within days); rate limiting/queueing; cost observability + kill switch; incident response. 4–8 weeks of engineering producing zero graph, zero schema, zero ledger. At €1–5/repo, stranger-adoption success scales costs with success against a €5–50k grant.
**(c) refused at M1, softer:** BYO-key removes cost exposure but keeps the worst part — custody of other people's provider keys (unscoped, breach liability) plus proxy liability (their key, our prompts, whose ToS violation?); quietly rebuilds most of (b)'s infra minus billing. The M1 recruit ("individual developers and small teams") is the most agent-saturated population on earth. Revisit at M2/M3 only on evidence of a real blocked population, and even then **prefer client-side key use (key never leaves the browser) over server custody**.
**Metering honesty:** verifiable = output conformance + prompt_hash against published prompt versions + digest consistency of a **run manifest** (run_id, model, prompt_hash, timestamps, input/output digests, self-reported tokens). NOT verifiable = token counts, actual model. No signature scheme fixes this at M1 (TEEs/provider receipts are blockchain-theater-adjacent here). **Self-attested metering is CORRECT at M1, not merely tolerable** — nothing economic hangs off token counts yet; the ledger records the claim and its verification level, never laundering claim into fact. Design constraint for adoption: the run-manifest format including the attestation enum (self-reported | platform-verified | future tiers) is part of the M1 schema from day one.
**PARAMOUNT:** no platform-paid inference at M1; **no server-side custody of user API keys at M1**; no ledger entry presenting self-attested counts without an explicit attestation label.

### Facilitator
Agreement: (a) BYO-agent skill is the M1 spine; platform ships prompts/schema/validator/CI + render-validate-ingest web app; q8b gates releases; submission gate at ingestion; run manifest with attestation enum from day one; self-attested runs = zero vu; no platform-paid inference (capped demo quota the only exception — PE to accept/reject).
ONE conflict: **the (c) metered on-ramp** — AE: BYO-key-via-platform-proxy must ship in M1.1 (the only path to auditable metering and the first vu-accruing agent runs; also non-Claude coverage); PE: no server-side key custody at M1 (paramount), revisit M2/M3, prefer client-side keys. Note for Round 2: is there a design satisfying both — e.g. client-side key with the browser calling the provider directly and submitting a run manifest (no custody, but counts stay self-reported), vs a metering proxy where the key transits but is never stored (custody-lite?), vs deferring vu-accruing agent runs to M2/M3 entirely (does anything at M1 actually NEED metered agent vu — 19p prices human hours; tokens-per-vu rates are delegated and unpriced)? Round 2 settles: when do metered agent runs actually need to exist, and what is the earliest custody-free design that serves it?
