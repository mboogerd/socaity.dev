# Council: socaity-z61 — Roadmap-as-graph medium at M0: how do believers contest edges before M1 tooling exists

Participants: community-builder, platform-engineer, product-designer
Type: research · Priority: P0 · Related: blocks socaity-ipg (first-contribution path); the M0→M1 retention mechanism

Issue:
- Context: milestones.md M0 requires the roadmap as the first needs graph, in the platform's own conventions, before any M1 tool exists; the graph doubles as what manifesto believers *do* between M0 and M1 (engagement + dogfooding).
- Question: What is the concrete M0 medium and workflow for reading the roadmap graph and contesting its edges — how does a stranger browse it, propose a node, dispute an edge, and see the live state — with zero platform tooling built?
- Why it matters: M0's retention depends on believers having structural work; the first contested edge is the first proof the conventions work.

Adopted context binding this council (do not relitigate):
- socaity-sbb: graph = one YAML per node in graph/nodes/ (schema:1, permanent n- IDs, slug sugar pinned at merge, edges inline in source node's file as refines/requires/equivalent_to records with provenance, estimates append-only, mandatory provenance block incl. human writes, CI validation); git history = M0 event log; PR diffs = the contestation record at N=1 (socaity-5u4: edit-with-history, dispute ceremony reserved for M4).
- socaity-7mk: contributor identity = keypair; GitHub linkage = revocable off-ledger attestation.
- socaity-19p/zjr: accepted graph contributions are ledger-eligible (0.5 vu floor, tickets for larger work).
- Prior recommendation on this issue (product-designer comment): static focus+context read view rendered from repo data; PR/issue-based edge contestation.
- Remaining scope: the reader experience (static site generation from graph/ files — what exactly renders at M0), the contest workflow mechanics (PR templates? who merges? how does "contested" show?), the contributor-facing conventions doc, and how this stays honest with sbb's status lifecycle.

## Round 1

### [community-builder]
PROPOSAL (owner). **1. On-ramp (stranger → actor in ten minutes):** manifesto's closing section links to ONE URL: the static graph view (built by CI from graph/nodes/, hosted on repo pages). Landing = the M0 root node with its refines/requires children, not the full graph. Every node card: title, status, one-line rationale, "View source" (deep-link to YAML at rendered commit) and "Contest this". Action menu, ascending effort: (1) watch/star + join the one channel (single Zulip/Discourse, public archives); (2) ask a question on a node (graph:question issue template — questions are contributions, they seed the FAQ); (3) propose a node / dispute an edge via PR. Paramount: the ten-minute path requires no account beyond GitHub and no reading beyond one conventions doc.
**2. Contest workflow:** propose-node.md PR template (schema:1 skeleton pre-filled, provenance block, CI checklist); dispute-edge.md (edit the source node's edge record; the PR diff IS the dispute record per 5u4; claim + proposed change + provenance; no counter-claim ritual at N=1 — the PR thread is the deliberation); graph:question issue template (zero-YAML on-ramp). Labels as the visible state machine: graph:proposal, graph:dispute, graph:accepted-pending-merge, first-contribution (auto-applied, priority response). **Who merges: founder solely at M0, bound by a published rule — merge criteria are structural (schema-valid, provenance complete, claim coherent), never agreement.** A well-formed dispute the founder disagrees with still merges; deadlock → edge marked contested rather than PR closed. A closed-without-merge dispute PR requires a written decision-record comment — the first silently closed dispute kills M0 retention. Turnaround SLO published: first response <24h weekdays; resolution or explicit cooling-off <7 days. Metrics: time-to-first-response; second-contribution rate.
**3. Contested state visible:** contested: <PR/issue URL> annotation on the edge record in the node YAML (set by trivial maintainer commit when a dispute PR opens; cleared by the resolving merge); render draws contested edges dashed/amber linking the open PR; **CI cross-check: an open graph:dispute PR with no matching annotation fails a scheduled check** — the render can never quietly hide a live dispute. Resolution is never deletion.
**4. Retention loop M0→M1:** merged graph contributions ledger-eligible per 19p (floor for small, tickets for larger); founder opens 5–10 **seeded contest tickets** on deliberately arguable edges/estimates, labeled good-first-dispute — contested edges by design, the argument IS the dogfooding; weekly ledger digest (merged nodes, resolved disputes, new entries by pseudonymous contributor) auto-generated from git history. Loop: read → contest → merged → ledger entry → named in digest → next dispute.
**5. Conventions doc:** graph/CONTRIBUTING.md, ≤2 pages: node anatomy by worked example, the two PR templates, merge rule + SLO, contested rendering, ledger credit basics, CoC link, escalation backstop. Schema spec is a separate reference, linked never duplicated.
**PARAMOUNT:** no back room (off-record graph decisions reconstructed as PR comments before merge); no invisible disputes (rather delay the pretty render than ship an opaque one); no merge-by-agreement (closing a well-formed dispute without a written decision record is the act I block consent on).

### [platform-engineer]
**1. Generator: one ~300-line Python script** at tools/render/ (PyYAML + jinja2, nothing else — no Hugo/Astro/Next; every framework is a dependency a forker inherits). Focus+context view as server-rendered HTML; a few KB of dependency-free inline JS max. **Lives in this repo — forkability requirement: git clone && python tools/render must produce byte-identical output to CI. The site is a pure function of the merged tree — that sentence is the entire architecture.** Build on every merge via one Actions workflow → Pages; PR builds upload preview artifacts. Also emit graph.json per build — the M1 ingestion seam and the export half of forkable (~20 lines now, saves a migration later).
**2. CI gates** (one offline validator at tools/validate/, required PR checks, diff-aware): schema:1 conformance; ID discipline (unique, never deleted/renamed); slug pinning enforced mechanically; referential integrity; provenance completeness including human writes, no exemptions; estimates append-only (byte-unchanged). Branch protection on these. That's the whole backend.
**3. Dispute → rendered state: a dispute is a PR editing the status field** with provenance pointing at the objection. Merge → rebuild → chip changes. **No dispute state lives outside graph/ files — if the site shows it, a file says it.** Asymmetric merge policy: **marking contested is a low-bar merge (near-unrefusable if CI passes); resolving is the high-bar merge** — that asymmetry keeps edit-with-history honest until M4.
**4. NOT built at M0:** live editing, accounts, database, API server, CRDT runtime (git merge IS the convergence layer at this scale), search service, notifications, graph-viz engine, ledger service (the ledger is a file in this repo under the same CI gates).
**5. Participation paths:** browser+GitHub: everything via GitHub web UI — "Edit this node" deep-links the web editor; issue templates for people who won't touch YAML, maintainer converts with provenance crediting the issue author. **Keypair-no-GitHub: the signed-patch courier path** — contributor signs canonical content (ssh-keygen -Y / minisign / PGP all accepted), sends patch + signature + pubkey to a published plain email inbox; maintainer opens the PR verbatim; provenance records the public key as author, embeds the signature; CI verifies. Documented before M0 is done, even if nobody uses it.
**PARAMOUNT:** no M0 component requiring a running server to know graph state (fork = clone + one command + same site); no renderer-private state (nothing on the site not derivable from graph/ files); no provenance exemptions for the founder; no shipping M0 GitHub-only (the signed-patch path is what makes 7mk's keypair identity true rather than aspirational). Build estimate: 2–3 founder-days.

### [product-designer]
**A.** Static site from graph/nodes/ — focus+context pages ARE the read model I'd ship with infinite budget; the generator is itself the first graph node with tickets on it. **B. Node page** (one URL per n- ID, slug redirects), one column, document aesthetic: breadcrumb trail of refines ancestors (orientation replaces the minimap); title + status chip (color + text label, never color alone; contested chip links the open PR); **provenance line as a designed object** ("Proposed by <keypair-name, GitHub-attested> · agent-drafted, human-reviewed · date · [history]") — agent authorship always labeled; need statement as prose; **"Requires" checklist** (status chip + title + estimate interval per row; done children struck through, not hidden); **"N competing approaches" as stacked cards, never tabs** (tabs hide alternatives); plain-language weights ("currently favored", "open") — **no probability decimals at M0**: no mechanism produces them honestly yet, fake precision is a trust leak; estimates as labeled interval bars with freshness stamps ("estimated 2026-07-30, 3 revisions — see all") — append-only history is a feature to show; See-also for equivalent_to; contest affordances in the footer. Every number/status links to its derivation.
**C. Entry points:** /roadmap = the root node page + one root-only element: the **"what matters now" strip** — 3–7 accepted, unblocked, unclaimed leaves, the standing invitation (the question canvases never answer). Manifesto links land on /roadmap, never an index or overview viz. /all index (flat, by status) for the auditor persona, deliberately boring. Optional build-time static SVG overview, purely illustrative; if it needs pan/zoom to be legible, cut it.
**D. Contest affordances:** "Contest this" → prefilled issue-form deep link (node ID, edge, structured fields: contest what / propose what / evidence) — commenting, not litigation; maintainer or contestant opens the PR editing the YAML. **Honesty rule: the contested chip derives from a machine-readable signal, never hand-maintained.** "Propose a change" → GitHub web-editor deep link; PR template enforces provenance; CI validates. Site renders contested while the PR is open, or contestation is invisible exactly when it matters.
**E. Ten-second diff:** one node or edge-set per PR; description wrapped ~72 chars; one edge record per line; estimates appended never edited. Plus: **CI posts a before/after render of the affected node-page section as a PR comment** (same generator, markdown target) — the single highest-leverage M0 build item after the site.
**F. Accessibility floor:** semantic HTML (nav breadcrumbs, real lists, sectioned cards); keyboard-traversable by construction; WCAG AA; no color-only status; text equivalents for bars; works CSS-off and at 200% zoom; no hover-only content.
**G. NOT at M0:** canvas/pan-zoom/force-directed anything; graph-editing UI; probability numbers, confidence scores, credit/multiplier/vesting surfaces; site-side comments/reactions (all discussion in the PR/issue record or the contestation record fragments); accounts, client-side state, analytics beyond privacy-safe counts.
**PARAMOUNT:** no interactive node-canvas in any form; no hand-maintained status (every chip derivable from repo state); no unlabeled agent-authored content; no point estimates anywhere. Validation: the 5-user comprehension test includes "starting from the manifesto, find what's blocking X and tell me how you'd disagree with it."

### Facilitator
Standing proposal: CB's workflow (templates, labels, structural merge rule, SLO, seeded disputes, digest, CONTRIBUTING.md) + PE's machinery (single-script generator + validator, pure-function-of-tree, graph.json, courier path, asymmetric merge bar) + PD's read model (node page spec, root strip, contest affordances, diff-render bot, accessibility floor).
Deltas for Round 2: (i) **contested-state signal** — CB: contested: <URL> annotation in the YAML (+ scheduled CI cross-check vs open dispute PRs); PE: dispute = PR editing the status field, no state outside graph/ files; PD: chip from a machine-readable signal "label or open PR". A GitHub label violates PE's no-renderer-private-state paramount. Reconcile to one mechanism — file-based state (status field or contested annotation, low-bar merge) as authoritative, with CB's scheduled cross-check as the drift alarm; PD to drop label-derived chips. Render labels may differ from storage enums (sbb: UI never teaches schema vocabulary) but need a published 1:1 mapping — settle it. (iii) Confirm CB's contested-annotation fits sbb's edge-record schema (provenance-adjacent field) — PE to rule. (iv) Minor: PD's "what matters now" strip needs "unclaimed" — is claim state a file field at M0 (tickets per 19p)? Define mechanically.
